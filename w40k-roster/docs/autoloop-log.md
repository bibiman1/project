# 自動改善ループ ログ

このファイルは、自動改善ループ（Web調査→実装との比較→改善実装→自己検証→マージ→次サイクル）の各サイクルが読み書きする引き継ぎメモ。各サイクルは記憶を持たない新規セッションとして起動するため、「何を調べたか」「何を実装したか」「次に何を調べるべきか」はすべてここに記録し、次のサイクルはここを読んでから作業を始める。

**大原則**: `docs/rules-notes.md` に記載済みの公式PDF（コアルール・陣営パック）由来の情報は、Web調査の結果より常に優先する。Web調査で複数の情報源が食い違い、かつ`docs/rules-notes.md`にも記載がない場合は、実装を変更せず「要確認」としてこのログに記録するにとどめ、コードは変更しない（不確実な情報を確信度なく実戦投入しない）。

## 運用ポリシー（2026年9月21日、ユーザー承認済み。同日中に2段階構成へ変更）

- 方針としては、調査→比較→実装→自己検証→コミット→PR→**マージ**までを人間の確認なしで自動実行することが理想（ユーザー承認済み）。ただし、Routineで自動起動する新規セッションにはGitHub PR作成ツール（`mcp__github__*`系）が一切付与できないというプラットフォーム側の制約があるとテスト発火（2026年9月21日）で判明した。専用のワーカーセッションを作成し`extra_allowed_tools`でツールを明示的に要求しても同じ制約を受けた。マージについても、自動マージを指示するRoutine作成が権限分類器に一度ブロックされている。これらはこのセッション側からは回避できない制約のため、下記の2段階構成で運用する。
- **段階A（ワーカーセッション、`session_01HQo19bJw5wBK2xd29YvfTM`、毎日03:00 UTC発火、trigger `trig_01PHXiWsmZyRi1uQ32nNWcz6`）**: 調査→比較→実装→自己検証→コミット→`origin/main`から切った新規ブランチ`autoloop/YYYY-MM-DD`へpushまで。git push権限はあるが、PR作成ツールがないためPRは作らない。
- **段階B（このセッション、毎日04:00 UTC発火、trigger `trig_0133sWSaeADqvyaZi6uLpP75`）**: `autoloop/`ブランチで未PRのものを探し、あればPRを作成する（GitHub PR作成ツールを持つのはこのセッションのみ）。マージはしない。
- マージはユーザー本人が判断する（PRが作成されたら通常のPR一覧で確認できる）。将来的にマージまで自動化したい場合は、権限分類器の制約が変わるか、別の方法が見つかった時点で再検討する。
- 復元ポイント: GitHubブランチ `restore-point/pre-autoloop-2026-09-21`（コミット `7a16c3f`）。何か問題が起きた場合、ユーザーの指示のもとここに戻せる。
- 1サイクルにつき変更は小さく絞る（大規模リファクタや無関係な変更はしない）。
- 段階Aは`autoloop/YYYY-MM-DD`という新規ブランチを毎回`origin/main`から作るため、このセッションが使う`claude/stoic-gates-22iefn`ブランチとは独立しており、rebase等の競合は発生しない。
- Playwrightでの自己検証を経ないままpush・PR作成しない。

### 2026-09-23（Web検索由来）

- **調査対象**: 次回調査候補1件目（デタッチメントのルール精度検証）として「ラドゾーン軍団」を選択。Wahapediaキャッシュ（`origin/wahapedia-cache`）にはユニットのデータシートHTMLのみ存在し、デタッチメントルール・策略・強化のページは含まれていなかったため、WebSearchで複数クエリを実行して調査した。
- **分かったこと**: WebSearch経由（wahapedia.ru・tabletopbattles.com等への直接WebFetchはネットワークプロキシでブロックされるため、検索結果のスニペット要約のみ利用可能）で、ラドゾーン軍団のデタッチメントルール（第1ラウンドの防御姿勢/隠れる選択とD6判定の閾値、第2〜5ラウンドのフォールアウト効果）、強化4種（放射拡散／マルフォニックの囁き／比類なき殲滅者／オートクレイヴの断罪）の効果概要、策略の一部（禍々しき光輪／防壁命令／事前較正殲滅解）を確認した。いずれも現在の実装内容と一致しており、不一致は見つからなかった。また、11版アデプトゥス・メカニカスの全7デタッチメント名とDP（戦闘サイズ）値も検索結果から確認でき、`js/detachments.js`内の7件全てが実在の正式デタッチメントでDP値も一致していることを確認した（検索結果には10版時代の旧デタッチメント名も雑音として混ざっていたため、DP値の一致で正式7件を裏取りした）。
- **実装内容**: ルール自体に修正は不要だったが、調査中に見つけたUI/UX改善点を1件実装。命令教条「征服命令」の条件付き効果（バトルラインユニットか、自軍バトルライン6"以内なら白兵武器の貫通値+1）は、これまで対象ユニットに関わらず一律「要手動反映」のテキストメモとして表示するだけだった。しかしこの条件の前半（ユニット自身がBATTLELINEキーワードを持つ）はユニットのキーワードだけで判定でき、位置情報は不要なため、`js/storage.js`の`computeUnitBuffs`でユニット自身がバトルラインなら白兵武器の貫通値+1を自動適用するよう変更（`ruleModifiers`と同じ`applyModifier`の仕組みを流用）。バトルラインでないユニットは従来通りテキストメモのまま（6"以内かどうかは位置情報がなく判定不可のため）。迎撃命令側の「被白兵ヒット-1」はこのアプリに「受ける攻撃への修正」を表現するフィールドがないため今回は対象外（次回調査候補に記載）。
- **自己検証**: 変更した`js/storage.js`を含む全JSファイルで`node --check`が通ることを確認。Playwright（`/opt/pw-browsers/chromium-1194/chrome-linux/chrome`）でローカルサーバー上の実際のページを開き、`window.W40K.computeUnitBuffs`をブラウザ内で直接呼び出して検証：①バトルラインキーワード持ちユニット＋征服命令 → 白兵武器の貫通値が自動で-1→-2に変化し「征服命令(バトルライン自動適用)」のメモが表示される、②バトルラインでないユニット＋征服命令 → 貫通値は変化せず従来通り「要手動反映」のメモが表示される、③迎撃命令 → 従来通り変更なし、の3パターンを確認。確認後サーバーは停止済み。
